# Service Contract Decisions

*Phase 3, task 3.4. Decided 2026-10-27 while reviewing the [service checklist](service-checklist.md). Each entry records a choice the Phase 4 controller and contract must follow, and why.*

These came from places where the hand-written payments manifests, the contract in architecture §9, or both, were not settled. Section references such as §2.5 point into the service checklist unless they say "architecture".

1. **One name for the service.** The ForgeService is named `payments`, matching the `app` label and the `<svc>-<kind>` resource names; architecture §9 and the examples use it. The application code and image keep the name payments-api (`examples/payments-api`, ECR `forge/payments-api`). Labels: every resource also carries `app.kubernetes.io/name: <svc>` and `app.kubernetes.io/managed-by: forge`, as metadata only. Selectors stay on `app: <svc>`, because a Deployment's selector is immutable and changing it later means recreating the Deployment. `app.kubernetes.io/instance` is not used, since Argo CD's label-based tracking uses it.
2. **Environment variables.** Added to the contract as `spec.env`, plain name and value pairs (architecture §6 and §9). It uses Forge's own type rather than the Kubernetes `EnvVar`, so `valueFrom` cannot reach arbitrary Secrets or ConfigMaps. Values live in Git, so secrets never go in it; secret references through External Secrets are a later, additive field. Still to define: validation of names (a valid identifier, no duplicates) and whether the platform reserves any names.
3. **CPU limits.** None. The contract accepts CPU and memory requests and a memory limit only; architecture §9 and §16.1 reflect this.
4. **Minimum replicas and the PDB.** The PDB uses `maxUnavailable: 1` (checklist §2.5), so `minReplicas: 1` is allowed, as the dev overlay in architecture §19 uses.
5. **`group.order`.** Omitted. It only matters when rules from two Ingresses can match the same request, and every service has its own host. That depends on two rules: one host per service, enforced by a Kyverno policy that rejects a host already used in the `forge-shared` group (architecture §16.2); and `ingress.path` routes within a service's own host, never between services sharing one. If shared hosts are ever wanted, the controller must order more specific paths first.
6. **`ingress.tls`.** Dropped. Every Ingress is HTTPS with a redirect from HTTP; there is no plain-HTTP option. Architecture §9 and §12 reflect this.
7. **Topology spread.** A topology spread constraint across nodes (checklist §2.1), not pod anti-affinity. Required anti-affinity needs a node per replica and leaves pods Pending once the NodePool limit is reached; preferred anti-affinity is treated as required by Karpenter during provisioning, so it can launch a node per replica. A spread with `maxSkew: 1` and `ScheduleAnyway` separates two replicas without tying node count to replica count, and never blocks scheduling. `matchLabelKeys: [pod-template-hash]` limits the spread to the current ReplicaSet during rollouts. Not rebalanced after an HPA scale-down until the next rollout or node replacement. Zone spread is left out: with a single NAT gateway an AZ failure already breaks egress.
8. **`awsAccess`.** Removed from the contract. The controller only renders Kubernetes objects, and an IAM role and Pod Identity association are AWS resources. A service that calls AWS gets them from Terraform, bound to `<svc>-sa` in its namespace, and every grant goes through a reviewed Terraform change. Architecture §6, §9, §13 and §24 reflect this. Design, to be built when the first service needs AWS access: one file per service that needs it (`infra/terraform/services/<svc>.yaml`, listing its namespaces and policy statements), read by a `service-identity` module that creates the role, an inline policy and one Pod Identity association per namespace for `<svc>-sa`. Pods already running when an association lands need a restart to pick up credentials. To settle at that point: a permissions boundary on every service role, and one role per environment rather than per service.
9. **Account-specific values.** Two kinds. Per-service values (name, host, image) are already in the contract; the controller derives every resource name from `metadata.name`, so the hardcoded `payments` names disappear in Phase 4. Installation values (account ID, region, cluster name, domain, ECR registry, public subnet CIDRs, metrics namespace) never enter the contract, which must not mention AWS. Terraform is their only source, set once at `make up`: it passes them as values on the root Argo CD Application it already creates, `charts/platform` becomes a small Helm chart that templates the platform Applications from them, and in Phase 4 the same chart renders the controller's ConfigMap. The controller reads it to render NetworkPolicy CIDRs and to reject hosts outside the domain; the CLI reads it, read-only, to default a new service's host and image repository. Terraform never needs a service name. The hand-written payments manifests keep their constants until the controller replaces them. Do the `charts/platform` conversion just before Phase 4.
10. **Kind name.** `ForgeService`, short name `fsvc`, so it never collides with the core Service. Architecture §6, §9 and the diagrams use it.
11. **`owner` and `slo`.** Nothing is rendered from them yet; they feed alert routing and the PrometheusRules in Phase 6.
12. **No `ingress.enabled` flag.** The `ingress` block is optional: present means an Ingress is rendered, absent means none. One way to express it, and no contradictory "disabled but with a host" case to validate.
13. **Status matches architecture §9 from the start,** including `errorBudget`, even though nothing populates it until the SLO work in Phase 6.
14. **Metrics are mandatory.** `observability` is required and has no `metrics` flag: every service exposes Prometheus metrics, because alerting and the SLOs depend on them. `metricsPort` is required and must differ from `runtime.port`; `metricsPath` defaults to `/metrics`. Every service gets a ServiceMonitor. This differs from Ingress (decision 12) on purpose: not every service needs a public route, but every service needs to be observable.
15. **`targetCPUUtilization` defaults to 75,** matching payments' HPA, so it can be omitted.
16. **Path fields share one rule:** `ingress.path`, `health.readiness`, `health.liveness` and `observability.metricsPath` must match `^/[A-Za-z0-9/._~-]*$`, a `/` followed by letters, digits and `/._~-`. The CLI's validation follows the same rule.
